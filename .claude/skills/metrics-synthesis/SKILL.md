# Metrics synthesis

The failure this exists to prevent: **re-deriving in Python what the monitoring
stack already computes, and getting a different answer.**

If a number in a notebook disagrees with the dashboard the team watches, the
notebook loses — and worse, nobody notices which one was wrong.

## The order to reach for things

| | use | not |
|---|---|---|
| a percentile | `histogram_quantile` over the bucket series | sorting N samples in Python |
| a trend | `query_range` | one scrape of `/metrics` |
| a panel's query | read it out of the dashboard JSON | write your own |
| a panel in a report | Grafana `/render` PNG | a matplotlib lookalike |

`benchmarking/prom.py` implements all four.

```python
from prom import Prom, Grafana, panel_queries, panel_id

p = Prom()                                   # :31490 through the tunnel
p.quantiles("ttft", qs=(0.5, 0.9, 0.99))     # real p50/p90/p99
p.query_range("vllm:kv_cache_usage_perc", minutes=30)
panel_queries("vllm")                        # what Grafana actually plots
Grafana(password=...).render("dodona-vllm", panel_id("vllm", "TTFT"), dest)
```

## Percentiles

vLLM publishes histograms. The percentile comes from the buckets:

```promql
histogram_quantile(0.99, sum by (le) (rate(vllm:time_to_first_token_seconds_bucket[5m])))
```

Ten samples sorted in Python gives a "p99" that is the maximum of ten, and it
moves wildly between runs. If a report quotes p99, it has to come from here.

Available: `e2e`, `ttft`, `tpot`, `queue`, `prefill`, `decode`.

## Reuse the dashboards' queries

The dashboards are generated by `infra/cluster/observability/dashboards.py`, so
their PromQL is already reviewed and is what the cluster is judged by.
`panel_queries("vllm")` returns it. A notebook that writes its own will drift.

## Traps that have actually bitten here

**`rate(sum(x)[5m])` is invalid.** It must be `sum(rate(x[5m]))`. Grafana
renders the first as an empty panel — indistinguishable from a metric that is
genuinely zero. `tests/test_dashboards.py` enforces this.

**An empty panel can be correct.** Before debugging one, ask what emits the
metric and whether that thing is deployed. Three panels here queried
`mooncake_*`, emitted by a pod no script ever applied. `Prom.series_exist()`
answers it: zero series means nothing scrapes it.

**Two metrics one word apart.** `prefix_cache_hits` is the pod's own cache;
`external_prefix_cache_hits` is the KV connector. An 87.9% local hit rate
beside zero transferred reads like the connector working. It is not.

**A lookup counter is not a transfer counter.** `external_prefix_cache_hits`
counts blocks *found*. The pull can still fail. `Num successful transfers` in
the engine log is the ground truth. This exact mistake produced a wrong result
here before it was caught.

**Counts in the request are not counts of work.** `prompt_tokens_total` counts
tokens in the request whether or not they were computed. The split is
`prompt_tokens_by_source{source=...}`: `local_compute`, `local_cache_hit`,
`external_kv_transfer`.

**A notebook that errors leaves its OLD outputs on disk.** `nbconvert
--execute --inplace` aborts without writing when a cell raises, so the file
still holds the previous run's results. Reading it then shows clean output and
plausible numbers from a run that no longer corresponds to the code. Both times
this happened here the stale table was almost reported as a finding. Check
nbconvert's own exit status and log — and beware `cmd | tail; echo $?`, which
reports tail's status, not nbconvert's.

**A notebook can pass on data that says it is broken.** The capacity sweep
printed `-95 requests`, three steps serving nothing, `running peak 0` while
supposedly serving, and KV frozen at one value across three load levels — then
concluded "capacity is 2 concurrent sessions" with every check PASS. Guard the
inputs, not just the result: did every step produce traffic, did any counter go
backwards, did a pod restart mid-run, and was the refusal a 503 or a 429?

**503 and 429 are different findings.** 503 is the cluster refusing on
capacity. 429 is a client quota and says nothing about the cluster. Counted
together, a rate-limited run is indistinguishable from a saturated one — which
is exactly how a broken tenant limiter capped a capacity measurement at 2
sessions on an H100.

## What makes it a result rather than a number

1. **Against an SLO.** "p95 TTFT 1.21s" is a number. "1.21s against a 1.5s
   promise" is a result. `benchmarking/slos.py` holds them; `Report.slo()`
   checks against them.
2. **With what was scarce beside it.** A latency figure cannot tell a policy
   that worked from one that never had anything to decide. Always report the
   peak of the signal the policy reads.
3. **One variable.** Same workload, same seed, one thing changed.
4. **Negatives included.** "Admission was neutral-to-negative because the GPU
   was never overwhelmed" is a stronger finding than a tuned win.

## Writing it up

Each notebook section: **question → measurement → chart → a conclusion computed
from the numbers just taken.** A chart without a sentence is left to the
reader, and a reader who must interpret it will interpret it the way they
already expected.

State what would falsify the claim before measuring it.
